# 00 · 设计思想：nx-pg 解决什么问题

> 本文档讲这个工具的来龙去脉：为什么存在、给谁用、什么场景用。
> 具体命令怎么调看 SKILL.md。

## 一、要解决的问题

**人机协作画布**场景里的两个老问题：

1. **AI 产出给人看，缺一块白板**。对话窗口里的层级文本（大纲、方案、任务分解）
   读起来费劲——人天然需要空间排版：树状、分组、连线。AI 的结构化内容
   应该「一键变成画布上排版好的思维导图」，而不是让用户复制粘贴重新排版。
2. **AI 看不见人看的东西**。用户在画布上整理了一半的思路、刚打开的文件，
   AI 一无所知，只能靠用户复述。上下文不对齐，协作就变成来回传话。

nx-pg 的回答：**画布文件是结构化数据（.prg），CLI 与面板操作同一套业务**——
AI 用 CLI 写新树进画布（人点链接就看），用 CLI 读画布内容与用户状态（对齐上下文再干活）。

## 二、使用背景

- 用户是**开着 nx-pg 面板工作的人**：画布常驻浏览器，随手整理想法、贴图、画结构
- 旁边跑着一个 AI agent（Claude Code 等）：能执行 shell 命令
- 两者的接驳点就是本机 HTTP 服务（127.0.0.1:7888）与等价 CLI——
  AI 不需要理解画布软件内部，只需要会三件事：

```
看状态:   canvas active / recent list     → 用户在看什么、最近看过什么
读内容:   canvas export                   → 画布里有什么（层级 md / json）
写内容:   canvas dag                      → 把一棵 md 树放到画布上（新文件）
```

## 三、典型使用场景

**场景 A · 快速初始化思路导图**（最常用）
用户：「把这段需求整理成导图」/ AI 手上有一份多级 md。
AI：`canvas dag --file 需求.md` → 把输出 URL 给用户 → 用户点开，画布上出现排版好的树。
不需要用户复制粘贴、手工建节点连线。

**场景 B · 基于用户已有画布继续工作**
用户画了一半的方案树，让 AI「补全剩余分支」。
AI：先 `canvas active` 知道用户在看哪个文件 → `canvas export --format md` 读出
现有层级 → 在**输出文件**里续写（绝不改用户原文件）→ 新文件 URL 交给用户对比。

**场景 C · 多方案并排对比**
AI 一次产出多个独立方案（或多份零散想法）。
一个 md 里用 `---` 切多块：每块独立成树、并排摆放、互不连线；
单行文本就是独立节点。一次生成，用户在画布上整体俯瞰。

**场景 D · 双向修改闭环**
AI 导出 md（`--format md`）→ 直接在文本上改层级 → 改完 `canvas dag` 导回画布。
md 是画布的「文本镜像」—— diff 友好，人和 AI 都能编辑。

## 四、行为约定（为什么这样设计）

1. **追加式**：AI 生成永远落新文件（重名自动 -2/-3）。AI 是「在旁边画的客人」，
   不动用户的原稿——误覆盖是不可逆的，宁可多一个文件。
2. **先读后写**：canvas active/recent/export 的存在就是为了「AI 别瞎猜用户在干嘛」。
   标准工作流要求生成前先对齐上下文。
3. **树优先，不碰环**：输入是嵌套 md（天然无环），输出是排版好的树。
   DAG 的共享子节点等复杂形态留待有真实需求再做——当前所有场景都是「发散树」（思维导图）。
4. **每步有反馈**：CLI 输出落盘路径、节点/连线统计、可点 URL——AI 能验证自己的
   操作结果，用户有明确的「去哪看」。

## 五、错误案例

| 踩过的坑 | 后果 | 正确做法 |
| --- | --- | --- |
| AI 把多行 md 塞进双引号参数（`\n` 当换行） | `\n` 是字面量，`---` 多块失效，整段变 1 个节点（静默） | `--file` 或 heredoc 传真实换行 |
| AI 不查 active/recent 直接生成 | 生成的树和用户正在看的内容对不上，用户要自己找文件 | 生成前先 `canvas active --json` |
| AI 试图修改用户已有 .prg | 不可能也不应该——CLI 只提供「生成新文件」 | 追加式：新文件 + URL 交付 |
| heredoc 的 flag 写在 EOF 之后 | 参数静默丢成默认值，树方向/名字不对 | flag 全在 `<<'EOF'` 之前 |
